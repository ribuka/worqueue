# Worqueue 仕様

プレイングマネージャー向けに、優先順位の可視化とタスク管理をまとめたアプリ。自分の実装の仕事と、チームの管理の仕事を 1 か所で俯瞰し、次に何をするかを決める。

## 名前（2026-11-22 ユーザー判断）

| 項目 | 内容 |
| --- | --- |
| 表記 | Worqueue |
| 読み方 | ワーキュー |
| 由来 | Work + Queue |
| リポジトリ名・パッケージ名 | `worqueue` |

- 理由：仕事を一覧するだけでなく、順番を決めて処理する（並べ替え、着手、委譲する）という意味がはっきりしているため。元の `Workqueue` のままだと一般的すぎるので、綴りを崩して造語にした。
- 候補だった `Workmap`（俯瞰を表す）と `Taskmix`（管理と実装の混在を表す）は採らなかった。

- `Worqueue` の綴りは、過去の技術文献やソースコードにも使用例がある。

## 解きたい課題

- プレイングマネージャーは、管理の仕事（レビュー、調整、メンバーへの依頼）と実装の仕事が混ざり、どれを先にやるべきかを判断しにくい。
- 自分の手元の仕事と、チームに振った仕事の全体像を同時に見たい。
- 単なる ToDo リストではなく、優先順位・進捗・依存関係を見て、次に着手する仕事を決められるようにする。
- タスクだけでなく、作業の履歴や判断（なぜその順にしたか）も残す。

## タスク（2026-11-22 ユーザー判断）

| 項目 | 内容 |
| --- | --- |
| タイトル | 1 行の名前（必須） |
| 状態 | 必須。`todo`（未着手）・`doing`（着手中）・`waiting`（相手の返事や他のタスクを待つ）・`done`（終わった）の 4 つ（2026-11-23 ユーザー判断）。メンバーに振った仕事も同じ値を使い、自分の仕事かどうかは担当で区別する。やめたタスクも `done` にし、やめた理由を履歴に書く |
| 本文 | 自由記述の説明（必須。空でもよい） |
| 種別 | 管理の仕事か、実装の仕事か。2 つの比率を見て、どちらかに偏っていることに気付けるようにする |
| 担当 | 自分か、チームのメンバー（名前）か。メンバーに振った仕事も、自分が追いかける仕事として同じキューに載せる |
| 期限 | 締め切りの日付（任意） |
| 依存関係 | 終わるのを待っている他のタスク（任意、複数可） |

- 理由：プレイングマネージャーの判断に要る「管理と実装のどちらに偏っているか」「誰の手にあるか」「いつまでか」「何に詰まっているか」を、それぞれ 1 項目で表せるようにするため。
- 重要度や緊急度の項目は持たない。順位は手で並べた順で表す（下の「優先順位」）。

## 優先順位（2026-11-22 ユーザー判断）

- キューの並び順そのものを優先順位とする。並べ替えるのは自分（またはエージェントが CLI で）。
- Worqueue はスコアを計算して自動で並べ替えはしない。並びを上げたほうがよさそうなタスクを指摘するだけにする。
- 理由：優先順位の判断は自分でしたいが、期限の近さや詰まりの見落としには気付きたいため。
- キューに載るのは `done` 以外のタスク。「上位 n 件」はキューの上からの n 件を指す。

### 並べ替えを指摘する条件（2026-11-23 ユーザー判断）

| 条件 | 内容 | しきい値の既定値 |
| --- | --- | --- |
| 期限が近いのに下 | 期限まで n 日以内（過ぎたものを含む）なのに、上位 m 件に入っていない | n = 3 日、m = 5 件 |
| 着手できるようになった | 依存先がすべて `done` になった。ただし自分が `doing` のものは除く | — |
| 振ったまま更新がない | 担当がメンバーで `done` 以外のタスクに、最後の履歴の追記（なければ作成）から n 日、追記がない | n = 7 日 |
| 他が待っている | このタスクの完了を待っている（依存先にしている）タスクより、並びが下にある | — |

- しきい値は設定で変えられるようにする（下の「設定」）。
- 指摘は並べ替えの候補を示すだけで、キューは変えない。

## 作業の履歴と判断（2026-11-22 ユーザー判断）

- 作業の経過と判断（なぜその順にしたか、なぜ振ったか等）は、そのタスクのファイルの末尾に、日時付きで追記する。
- 理由：1 件の経緯をまとめて読めるようにするため。
- 並べ替えの理由は、動かしたタスクのファイルに書く。
- Worqueue が書く履歴の行の内容（2026-11-25 決定）：
  - `wq add`：`作成`
  - `wq move --reason <理由>`（動いたときだけ）：`移動 <from> → <to>: <理由>`。理由なしの `wq move` は履歴に書かない（何が動いたかは `data/` の git に残る）。
  - `wq done`：`完了`（`--reason` があれば `完了: <理由>`）
  - `wq log <ID> <内容>`：`<内容>` そのまま
  - `wq edit`（何かを変えたときだけ）：`<変更の文>`（`--reason` があれば `<変更の文>: <理由>`）。例：`状態 todo → doing、担当 me → 佐藤`（下の「`wq edit <ID>`」）
  - 理由：コミットのメッセージの `move 42: 7 → 2` と同じ向きで読める。
- 履歴の足し方（`store/task.py` の `append_history`。2026-11-25 決定）：
  - Markdown に `## 履歴` だけの行があるとき：末尾の改行を除き、最後の空でない行が `## 履歴` なら空行 1 つを挟んで、そうでなければ改行 1 つの後に、履歴の行と改行を足す。`## 履歴` より後に手で書いた見出しや文があっても、その後（ファイルの末尾）に足す。
  - 無いとき：末尾の改行を除いた Markdown が空なら `\n## 履歴\n\n<行>\n`、空でなければ `<Markdown>\n\n## 履歴\n\n<行>\n`。
  - 例：`\n本文\n\n## 履歴\n\n- 2026-11-24 09:10 作成\n` に足すと `\n本文\n\n## 履歴\n\n- 2026-11-24 09:10 作成\n- 2026-11-25 10:00 <内容>\n`。

## データの置き場所（2026-11-22 ユーザー判断）

- worqueue のリポジトリ直下の `data/` に置く。
  - 理由：データは Worqueue でしか使わないので、アプリのそばに置く。
  - 場所はパッケージの場所から求める：`Path(worqueue.__file__).resolve().parents[2] / "data"`（`src/worqueue/__init__.py` → `src/worqueue` → `src` → リポジトリ直下）。どのフォルダから実行しても同じ `data/` になる。worktree では worktree の `data`（メインの `data/` へのジャンクション。下の「worktree の `data/`」）になる（2026-11-24 ユーザー判断）。
  - 環境変数 `WORQUEUE_DATA` が空でなければ、そのパスを `data/` とする。テストはすべて、`tests/conftest.py` の autouse の fixture でこれを一時ディレクトリにして、本物の `data/` に書けないようにする。同じ fixture で git をユーザーの設定から切り離す（`GIT_CONFIG_GLOBAL` を空のファイル、`GIT_CONFIG_NOSYSTEM=1`、コミットする人を環境変数で渡す）。ユーザーの hook や署名の設定でテストが変わらないようにするため。
- worqueue のリポジトリでは `.gitignore` の `/data` で除外する。`data/` の中は、それ自体を独立した git リポジトリにして追跡する。
  - 2 つの git の役割：worqueue のリポジトリはコードを、`data/` のリポジトリはタスクの変更を追跡する。タスクのファイルへの追記（上の「作業の履歴と判断」）には判断の理由を書き、`data/` の git には何が変わったかが残る。
  - `/data/`（末尾に `/`）ではなく `/data` にする。git はシンボリックリンクをフォルダではなくファイルとして扱うので、`/data/` ではシンボリックリンクの `data` を除外できないため（2026-11-22 確認）。
- `data/` のコミットは、Worqueue が CLI で書き込むたびに自動で行う（2026-11-23 ユーザー判断）。
  - 理由：履歴を取りこぼさないため。自分でコミットするのを忘れると、何がいつ変わったかが残らない。
  - 1 回の操作 = 1 コミットにする。メッセージは `<操作> <ID>: <内容>` の形で操作から作る。`wq add` は `add <ID>: <タイトル>`（2026-11-24 ユーザー判断）。`wq move` は `move <ID>: <from> → <to>`、`wq done` は `done <ID>: <タイトル>`、`wq log` は `log <ID>: <内容>`、`wq edit` は `edit <ID>: <変更の文>`（2026-11-25 決定。`log` の内容やタイトルの変更が長いとメッセージも長くなるが、受け入れる）。残る操作の内容は、その操作を作るときに決める。
  - 何も変えない操作（`wq move` で今と同じ位置へ動かす、`wq edit` で今と同じ値にする）は、何も書かず、コミットもしない。
  - 自分がエディタでファイルを直接直したときは、自分でコミットする。Worqueue は、未コミットの変更が残っていても書き込みを止めない。
  - 自動コミットには、その操作で Worqueue が書いたファイルだけを入れる：`git add -- <paths>` のあと `git commit -m <message> -- <paths>`（2026-11-24 ユーザー判断）。
    - 理由：手で直したままの変更を勝手にコミットしないため。同じファイルを手で直していたら、その変更は一緒に入る。これは受け入れる。
  - `data/` がまだ git のリポジトリでなければ、最初の書き込みで `git init -b main` し、`.gitignore`（中身は `.lock` の 1 行）を書いて、最初のコミットに入れる（2026-11-24 ユーザー判断）。
    - リポジトリかどうかは `data/.git` があるかで決める。`data/` は worqueue のリポジトリの中にあるので、`git rev-parse` は外側の worqueue のリポジトリを見つけてしまう。git のコマンドは `git -C <data>` で実行する。
  - 読むだけの操作（`wq list`・`wq show`）は、`data/` も git のリポジトリも作らない。
- `data/` のリポジトリのバックアップ（remote への push）は、今はしない（2026-11-23 ユーザー判断）。

### worktree の `data/`（2026-11-22 ユーザー判断・実装）

worktree はそれぞれ別の作業フォルダなので、追跡しない `data/` は worktree ごとにできてしまう。worktree で CLI を試すと、別の `data/` を読み書きすることになる。そこで、worktree の `data/` を、メインのチェックアウトの `data/` へのジャンクションにする。

- `.githooks/post-checkout` が、PowerShell のスクリプト `.githooks/_link-data.ps1` を呼ぶ。`git worktree add` の直後にも呼ばれる。chatgpt-vault の `config/settings.local.toml` のリンク（`.githooks/_link-local-settings.ps1`）を流用した。
  1. メインのチェックアウトのパスを、`git rev-parse --git-common-dir` の親フォルダとして得る。今の worktree がメインなら何もしない。
  2. 今の worktree に `data` がすでにあれば（壊れたリンクも「ある」とみなす）何もしない。毎回のチェックアウトで呼ばれるが、これで害はない。
  3. メインに `data/` がなければ先に作る。worktree が自分だけの `data/` を持つことがないようにするため（流用元は、リンク先がなければリンクしない）。
  4. ジャンクションを作る。
- リンクを作れなかったとき（`pwsh` がないなど）は警告を出すだけにし、チェックアウトは失敗させない。コピーは作らない。
- シンボリックリンクではなくジャンクションにする（流用元はシンボリックリンク）。理由：フォルダへのリンクなら、ジャンクションは開発者モードも管理者権限も要らないため。
- 有効にするには、クローンごとに 1 回 `git config core.hooksPath .githooks` を実行する（すべての worktree に効く）。hook を有効にする前からある worktree では、その worktree で `pwsh -NoProfile -File .githooks/_link-data.ps1` を実行する。
- 確認したこと（2026-11-22、この PC。Git for Windows 2.54.0、PowerShell 7.7.0）：
  - `git worktree add` の直後にジャンクションが作られる。メインに `data/` がなければ、メインに作られてからリンクされる。
  - シンボリックリンクとジャンクションのどちらでも、`git worktree remove --force` で worktree を消すとリンクだけが消え、リンク先（メインの `data/`）の中身は残る。
  - `rm -rf`・`Remove-Item -Recurse`・`git clean -fdx` で worktree を消したときにリンク先が残るかは確かめていない。この環境では hook がこれらの削除を禁じている。Orca が worktree を消すときの方法も確かめていない。
- テストは一時ディレクトリを渡して、本物の `data/` に触れない。

## データの形式（2026-11-23 ユーザー判断）

```
data/
  .git/           data/ のリポジトリ（最初の書き込みで作る）
  .gitignore      中身は ".lock" の 1 行（最初の書き込みで作る）
  .lock           書き込みのロック（追跡しない。下の「同時の書き込み」）
  config.toml     設定（任意。wq は作らない。下の「設定」）
  next_id         次に使う ID
  queue.md        キューの並び順（タスクの ID を上から並べる）
  tasks/
    1.md          1 タスク = 1 ファイル
    2.md
```

- ファイルはどれも UTF-8、改行は LF で書く。

- タスクのファイルは Markdown + front matter（YAML）。項目は front matter に、本文と履歴は Markdown に書く。
  - 理由：人もエージェントもそのまま読めて、エディタで直すこともでき、履歴の追記も自然に書けるため。TOML は長い本文が書きにくく、JSON は人が直接直すのに向かない。
- タスクの ID は連番（1、2、3 …）。ファイル名は `tasks/<ID>.md`。一度使った番号は再利用しない。
  - 理由：CLI で打ちやすく、会話でも「42 番」と呼べるため。タイトルをファイル名に入れると、タイトルを変えたときに名前とずれる。
- キューの並び順は `queue.md` の 1 ファイルに、タスクの ID を上から並べて持つ。
  - 理由：並べ替えが 1 ファイルの変更で済み、`data/` の git の差分も「どれがどこへ動いたか」として読める。各タスクに順位の項目を持たせると、1 件動かすだけで他のタスクのファイルまで書き換わることがある。
  - `done` にしたタスクはキューから外す。

### `queue.md` と `next_id` の書き方（2026-11-24 ユーザー判断）

`queue.md` は、見出しの下に ID だけの箇条書きを上から並べる。

```markdown
# Queue

- 40
- 42
- 38
```

- 理由：並べ替え以外の差分が混ざらない。タイトルは `data/` の git のコミットのメッセージで読める。
- 書くとき：`# Queue\n` の次に、空でなければ空行 1 つと `- <ID>` の行を上から並べる。
- 読むとき：`- <ID>`（`^- (\d+)\s*$`）の行を上から順に取る。`#` で始まる行と空行は読み飛ばす。それ以外の行と、同じ ID が 2 回目に出る行は、行番号を含むエラーにする。ファイルがなければ空のキュー。
- キューにある ID のタスクのファイルがなければ、キューのタスクを読む操作（`wq list`・`wq add`・`wq show`・`wq move`・`wq log`・`wq edit`）はエラーにする（ID を含む）。手でタスクを消すときは、`queue.md` の行も消す。

`next_id` は、次に使う ID（整数 1 つと改行。例：`43\n`）を持つ。

- 理由：手でタスクのファイルを消しても、番号を再利用しない（番号の意味がずれない）。使ってみて変えるかもしれない。
- 次の ID は `max(next_id の値, tasks/ の中の最大の ID + 1)`。どちらもなければ 1。タスクを作ったら `ID + 1` を書く。`next_id` を消しても、`tasks/` から続きの番号になる。

### タスクのファイルの書き方（2026-11-23 ユーザー判断）

- 項目の名前は英語：`title`・`status`・`kind`・`assignee`・`due`・`depends_on`・`created`。
- `kind` は `manage`（管理）か `implement`（実装）。`assignee` は自分なら `me`、メンバーならその名前。`due` は日付（`YYYY-MM-DD`）、`created` はタイムゾーン付きの日時。
- 本文のあとに `## 履歴` の見出しを置き、`- <日時> <内容>` の箇条書きで追記する。

例：

```markdown
---
title: API の設計をレビューする
status: waiting
kind: manage        # manage（管理）か implement（実装）
assignee: 佐藤       # me（自分）かメンバーの名前
due: 2026-11-27
depends_on: [38]
```

### 同時の書き込み（2026-11-23 ユーザー判断）

CLI（エージェント）と Web UI とエディタが、同じファイルを同時に書くことがある。

- 書き込みは `data/` のロックファイルで 1 つずつにする。ロックを取ったら、変更するファイルを読み直してから変更し、コミットまで済ませてからロックを外す。
- Web UI は、画面を開いた（読んだ）あとにファイルが変わっていたら、上書きせずに知らせる。
- エディタはロックを取らない。エディタで直している最中に Worqueue が同じファイルを書く衝突は防げないが、`data/` の git で戻せる。
- ロックは `filelock.FileLock(data/.lock, timeout=10)`（2026-11-24 ユーザー判断）。
  - OS のファイルのロックなので、プロセスが落ちてもロックは残らない。残ったときの扱いは要らない。
  - 10 秒で取れなければ、何も書かずにエラーにする。1 回の書き込みは一瞬なので普通は待つだけで済み、固まったときも CLI は止まらない。
- 書き込みの手順（2026-11-24 ユーザー判断）：
  1. 書く前に、`git` が使えること（`git --version`）と、コミットする人が決まっていること（`git var GIT_COMMITTER_IDENT`）を確かめる。だめなら何も書かずにエラーにする。
     - コミットする人は、コミットで使われる設定で確かめる：`data/.git` があれば `git -C <data>`、なければグローバルとシステムの設定だけ（空の一時ディレクトリで、`GIT_CEILING_DIRECTORIES` をその親にして実行する）。新しく `git init` する `data/` のリポジトリは、外側の worqueue のリポジトリのローカルの設定を引き継がないため。
  2. `data/` がなければ作り、ロックを取る。
  3. 使うファイルを読み直し、入力を確かめる（依存先があるか、など）。ここまでのエラーでは何も書かない。
  4. `data/.git` がなければ `git init` する（上の「データの置き場所」）。
  5. ファイルは一時ファイルに書いて `os.replace` で置き換える。`wq add` は、タスクのファイル → `next_id` → `queue.md` の順に書く。
  6. 書いたファイルだけをコミットし、ロックを外す。
  - 書いたあとにコミットが失敗したら、書いたファイルは戻さず、「ファイルは書いたがコミットできなかった」と分かるエラーにする。理由：書いてからの失敗はまれで、戻すとかえってデータを失いうるため。
- 読むだけの操作はロックを取らない。一時ファイル + `os.replace` で書くので、読む側は書きかけのファイルを見ない。タスクのファイルを `queue.md` より先に書くので、キューにあるのにファイルがない状態も見ない。複数のファイルにまたがる読みは一貫しないことがあるが、受け入れる。
- Web UI は、読んだファイルの版を書き込みのときに渡し、ロックの下で照合する（下の「Web UI の変更の見分け方」）。

### Web UI のキューの一覧（2026-11-25 決定）

- 上の帯：`Worqueue`、キューの件数、管理と実装の比率（`管理 <n>（<p>%） / 実装 <m>（<q>%）`。`p`・`q` は四捨五入した整数。空なら `管理 0 / 実装 0`）、エラーの帯。
- 追加のフォーム：タイトル・種別（既定 `implement`）・担当（既定 `me`）・期限。`wq add` は `--kind` を必須にしているが、画面の選択には初期値が要るため。
- 表：`#`・`ID`・タイトル・状態・種別・担当・期限。行をドラッグして別の行に落とすと動く。落とした行の上半分ならその行の前、下半分ならその次の行の前（最後の行なら末尾）。行き先が今の位置と同じなら何も送らない。ドラッグでの並べ替えは理由を書かない。
- 行をクリックすると、横に詳細を開く：項目の編集（開いたときから変わった項目だけを送る。依存先は `,` 区切りの ID）、履歴（`## 履歴` の行より後を、前後の空行を除いてそのまま）、履歴の追記、完了（理由は任意）。
- 詳細の読み込みは、開くたび・閉じるたびに世代を進め、古い世代の応答は捨てる。1 → 2 と続けて開いたときに 1 の遅い応答で 2 の入力が消えたり、閉じた後に開き直したりしないようにするため。
- 書き込みが成功したら、一覧と詳細を読み直す（入力中の値は捨てる）。エラーはエラーの帯に出し、409 のときは読み直す。画面の自動の更新（ポーリングなど）はしない。ファイルの変化は書き込みのときの 409 で知らせる。

### Web UI のかんばん（2026-11-25 決定。Issue #15）

- 列は左から `todo`・`doing`・`waiting`・`done`。見出しは状態の値と件数（`done` の列は `done` のタスク全体の数）。
- `todo`・`doing`・`waiting` の列は、`GET /api/queue` のタスクを状態で分け、キューの順に上から並べる。`done` の列は `GET /api/done` のタスク（ID の大きい順に最大 20 件）で、それより多ければ列の最後に `ほか <n> 件`。
  - 理由：`done` のタスクは増え続けるので上限を置く。完了の日時は front matter に無いので、ID（作った順）で近いものを出す。古いタスクを今日完了しても列に出ないことがあるが、受け入れる。
- カード：`#<位置>`（`done` の列では出さない）・ID・タイトル・種別・担当・期限。`done` 以外のカードをクリックすると、キューの一覧と同じ詳細パネルを開く。`done` のカードは何もしない（詳細パネルは `done` のタスクを開かない）。

かんばんでの移動とキューの並び順の関係：

- 落とした位置は、ポインタより上に縦の中央があるカードの数 `place`（列の中で、その添字の前に入る）。
- 同じ列の中（`todo`・`doing`・`waiting`）の上下の移動は、キューの並び順を変える（状態は変えない）。列のカードの並び `C`（キューの順）で、動かすカードの添字を `d` とする。
  - `place == d` か `d + 1` なら何も送らない。
  - `place < len(C)` なら `C[place]` の直前へ（`move` の `before: C[place].id`）。
  - `place == len(C)` なら列の最後のカードの直後へ：キューの全体から動かすカードを除いた並びで、`C[-1]` の次のタスクの ID を `before` にする（無ければ `null`＝末尾）。例：`1(todo) 2(doing) 3(todo)` で 1 を 3 の下へ → `2 3 1`。
  - 理由：優先順位はキューの 1 本の並びで表す（「優先順位」）ので、列ごとの並び順は持たない。列の中の見た目の順がいつもキューの順と一致し、既存の `move`（`before`）の 1 コミットで書ける。狙ったカードとの間にある他の列のタスクを飛び越えるが、列の中の順を変えたいという意図に合うので受け入れる。列の最後の下でキューの末尾へ送ると、他の列のタスクの後ろまで下がりすぎる。
  - 書き込みはキューの一覧のドラッグと同じ（`queue.md` の版、理由なし）。
- 列の間の移動は状態だけを変える。キューの並び順は変えず、落とした位置は使わない（カードは新しい列の中で、キューの順の位置に出る）。
  - `todo`・`doing`・`waiting` の間、および `done` の列からそれらへ：`PATCH /api/tasks/{id}` に `{"version", "status"}`。`done` から戻すと `edit_task` の決まりどおりキューの末尾に入る。
  - `done` の列へ：`POST /api/tasks/{id}/done`（理由なし）。理由を書くなら詳細パネルの完了を使う。
  - 渡す版は、カードを描いたときの `task_versions` の版（無ければ `"none"` で 409 になる）。書き込みの直前に読み直した版では、画面を読んだ後に CLI で変わった状態を黙って上書きしてしまうため。
  - 理由：状態を変えたことで優先順位が暗黙に動かないようにし、1 回のドラッグ = 1 回の操作 = 1 コミットを保つ。
- `done` の列の中の移動は何も送らない（`done` のタスクには並び順が無い）。
- 書き込みの後の読み直しとエラーの出し方は、キューの一覧と同じ（409 なら読み直す）。

### Web UI の変更の見分け方（2026-11-25 決定）

- ファイルの版は、中身のバイト列の SHA-256（ファイルが無ければ `"none"`。`store/versions.py` の `file_version`）。
  - 理由：mtime は粒度と、エディタの書き戻しで見逃しうる。中身を比べれば、エディタでの変更も確実に見分けられる。
- 画面は読んだときの版を持ち、書き込みで渡す。`edit_task`・`log_task`・`done_task`・`move_task` はキーワード引数 `expected`（`FileVersion` の並び）を受け取り、ロックを取った直後、読む前に照合する。違えば何も書かずに `StaleError`（`WorqueueError` の子）：`<data/ からの相対パス> は画面を読み込んだ後に変わりました。読み込み直してください`。CLI は渡さない。
- 照合するファイル：編集・追記・完了（かんばんでの状態の変更と完了を含む）はそのタスクのファイル。並べ替え（かんばんの列の中の移動を含む）は `queue.md` だけ。
  - 理由：並べ替えは行き先を位置ではなく `before`（行の ID）で指すので、他のタスクの状態が変わっても狙った行の前に入る。行き先が `done` になっていれば `move_task` のエラーになる。他のタスクを編集するたびに並べ替えが 409 にならないようにするため。
- 読む API は、版を先に読み、それから中身を読む。間で変わっても版が古くなるだけ（409 になるだけで、上書きはしない）。

### Web UI の API（2026-11-25 決定）

`web/app.py`。どれも JSON を返し、書き込みは `store/ops.py` の操作を通す（1 回 1 コミット）。

| メソッドとパス | 本体 | 成功の応答 |
| --- | --- | --- |
| `GET /api/queue` | — | `{"tasks": [<タスクの JSON>, ...], "version": <queue.md の版>, "task_versions": {"<ID>": <タスクのファイルの版>, ...}}` |
| `GET /api/done` | — | `{"tasks": [<タスクの JSON（position は null）>, ...], "total": <done の件数>, "task_versions": {"<ID>": <版>, ...}}` |
| `GET /api/tasks/{id}` | — | `{"task": <wq show --json の task>, "body": <本文>, "version": <タスクのファイルの版>}` |
| `POST /api/tasks` | `title`・`kind`（必須）、`assignee`・`due`・`depends_on`・`status`・`body` | 201 `{"task": ...}` |
| `PATCH /api/tasks/{id}` | `version`（必須）、`title`・`status`・`kind`・`assignee`・`due`・`depends_on`・`body`・`reason` | `{"task": ..., "changed": [...]}` |
| `POST /api/tasks/{id}/log` | `version`・`content` | `{"task": ...}` |
| `POST /api/tasks/{id}/done` | `version`、`reason` | `{"task": ...}`（`position` は `null`） |
| `POST /api/tasks/{id}/move` | `version`（`queue.md` の版）・`before`（ID か `null`＝末尾。必須） | `{"task": ..., "from": <from>}` |

- 応答の形は、対応する CLI の `--json` と同じ。
- `task_versions` は、応答の `tasks` の各タスクのファイルの版（キーは ID の文字列）。かんばんで状態を変えるときに渡す。`tasks` の各要素の形を CLI の `--json` と同じに保つため、別の項目にする。
  - `GET /api/queue` は `queue.md` の版 → `queue.md` の ID ごとのタスクのファイルの版 → `list_queue` の順に読む。間で `queue.md` が変わり、`tasks` に版を読んでいない ID が出たら、その版は `"none"`（書き込みは 409 になる）。
  - `GET /api/done` は `tasks/` のすべてのタスクのファイルの版 → `list_done` の順に読む。`tasks` は `list_done`（`done` のタスクを ID の大きい順。`store/ops.py`）の先頭 20 件、`total` はその件数。`data/` が無くても何も作らない。`list_done` はすべてのタスクのファイルを読むので、`done` でないタスクのファイルが壊れていても 400 になる。
- 本体は pydantic（`web/bodies.py`）。未知のキーは 422。`PATCH` で省いた項目は変えない。`due: null` は期限を消す。それ以外の項目の `null` は 422。
- `PATCH` の `depends_on` は依存先の全体。`TaskEdit.depends_on` として渡し、`edit_task` がロックの下で版を照合した後に読んだファイルの依存先との差を、外す ID と足す ID にする（残る ID は今の順のまま、足す ID は指定の順で後ろに続く）。確かめるのは足す ID だけ。今からある依存先を確かめ直さないという `wq edit` の決まりを保つため。サーバーが照合の前にファイルを読まないので、画面を開いた後にファイルが消えたり壊れたりしても 409 になる。
- エラーは `{"error": "<メッセージ>"}`。`StaleError` は 409、その他の `WorqueueError`（タスクが無いときも）は 400。本体の型の誤りは FastAPI の既定の 422。
- 守り（`web/guard.py`）：`Host` の名前が `127.0.0.1` か `localhost` でなければ 403（DNS rebinding を防ぐ）。GET・HEAD 以外で `Content-Type` が `application/json` でなければ 415（他のサイトのページからの書き込みはプリフライトが要るようになり、CORS を許さないので通らない）。トークンでの認証は持たない（自分専用の PC で使うため。ddviz のトークンは共有の RDP サーバーのため）。

### CLI のコマンド（2026-11-23 ユーザー判断）

- コマンド名は `wq`。`worqueue` という別名は作らない。開発中は `uv run -m worqueue` でも同じものを呼べる。
- git と同じく、主役（タスク）の操作は動詞を直下に置き、脇役の対象は名詞でまとめる。
  - 理由：操作のほとんどはタスクへの操作なので、よく使う操作を短く打てる。並び順もタスクの位置、指摘もタスクの見方なので、対象が増えても直下の動詞は散らかりにくい。名詞 + 動詞に統一すると、毎回 `task` を打つことになる。
  - 新しい脇役の対象（例：メンバーの一覧）を足すときは、名詞のグループにする（`wq member add` など）。

| コマンド | 内容 |
| --- | --- |
| `wq add <タイトル>` | タスクを作り、キューの末尾に入れる。項目はオプションで指定する |
| `wq list` | キューを上から表示する |

| `wq edit <ID>` | 項目を変える |

| `wq serve` | Web UI のサーバーを立てる（下の「`wq serve`」） |

### CLI の共通の動き（2026-11-24 ユーザー判断）

- コマンド名は `pyproject.toml` の `[project.scripts]` の `wq = "worqueue.cli.app:main"`。`uv run -m worqueue` も同じ `main` を呼ぶ。

| --- | --- | --- |
| 成功 | 0 | 標準出力 |

- 理由：エージェントは終了コードで成否を、`--json` の標準エラーで理由を機械的に読める。

### `wq list`（2026-11-24 ユーザー判断）

- キューを上から表示する。キューにないタスクは出さない。キューに残っていても `status` が `done` のタスク（手で直した場合）は出さない。
- 人向けの出力：

  ```
  #  ID  STATUS   KIND       ASSIGNEE  DUE         TITLE
  1  40  doing    manage     me        2026-11-24  リリースの判断
  2  42  waiting  manage     佐藤      2026-11-27  API の設計をレビューする
  3  38  todo     implement  me        -           仕様を書く
  ```

  - 列は 2 つの空白で区切って左に揃える。幅は `unicodedata.east_asian_width` が `W`・`F` の文字を 2 として数える。最後の列（TITLE）は埋めない。期限がなければ `-`。
  - 理由：属性の列が揃い、タイトルが長くても崩れない。
  - キューが空（`data/` や `queue.md` がない場合も）なら `キューは空です` の 1 行。
- JSON：`{"tasks": [<タスクの JSON>, ...]}`（空なら `{"tasks": []}`）。
  - 理由：あとで指摘や比率を横に足しても形が壊れない。

### `wq show`・`wq move`・`wq done`・`wq log`・`wq edit` の共通（2026-11-25 決定）

- `<ID>` は位置引数の整数（argparse の `type=int`。整数でなければ終了コード 2）。
- `<ID>` のタスクのファイル（`tasks/<ID>.md`）が無ければ `タスク <ID> がありません`（終了コード 1）。
- 「位置」は、`wq list` で出すタスク（`queue.md` にあり `done` でないもの）の中での 1 から始まる位置。`queue.md` に手で残した `done` のタスクは数えない。位置を持たないタスク（`done`、または `queue.md` に無い）もある。
- 書き込む 4 つ（`move`・`done`・`log`・`edit`）の流れは `wq add` と同じ（「同時の書き込み」の「書き込みの手順」）。確かめる段階のエラーでは何も書かない。`store/ops.py` の非公開の `_write_locked` が、git の確認 → `data/` を作る → ロック → 呼び出し側の「読んで確かめ、書くファイルとメッセージを決める」部分 → `ensure_repo` → 書く → コミットを行う。呼び出し側が何も変えないと返したら、書かずにコミットもしない。
- `show` はロックを取らず、何も作らない。
- 理由（`--reason`）・内容（`wq log` の `<内容>`）は前後の空白を除く。空なら `<名前>が空です`、改行を含めば `<名前>に改行は入れられません`（終了コード 1。`<名前>` は `理由`・`内容`）。`wq add` のタイトルと同じ規則。
- 時刻は `cli/clock.py` の `now()`（`datetime.now().astimezone()`）から取る。`wq add` も同じ。テストは `tests/cli/conftest.py` の `wq` の fixture でこれだけを差し替える。

### `wq show <ID>`（2026-11-25 決定）

| 引数 | 内容 |
| --- | --- |
| `<ID>` | 必須 |
| `--json` | タスクを JSON で出す |

- 1 件の項目・本文・履歴を出す。`done` のタスクやキューに無いタスクも出す。何も書かない。
- 人向けの出力：

  ```
  ID:         42
  TITLE:      API の設計をレビューする
  STATUS:     waiting
  KIND:       manage
  ASSIGNEE:   佐藤
  DUE:        2026-11-27
  DEPENDS_ON: 38, 40
  CREATED:    2026-11-24T09:10:00+09:00
  POSITION:   2

  API のエンドポイントの命名をそろえる。

  ## 履歴

  - 2026-11-24 09:10 作成
  ```

  - 項目の行は `<名前>:` を 12 文字（`DEPENDS_ON: ` の長さ）に空白で埋め、値を続ける。名前は `wq list` の列名と同じ。
  - `DUE` が無ければ `-`、`DEPENDS_ON` が空なら `-`、複数なら `, ` でつなぐ。`POSITION` は位置、無ければ `-`。
  - 項目の行の後に、空行 1 つと、Markdown の先頭と末尾の改行を除いたものを出す。それが空なら空行も出さない。
  - 理由：本文と履歴は書いたとおりに読める。
- JSON：`{"task": <タスクの JSON に "markdown" を足したもの>}`。`"markdown"` は front matter の後の Markdown から先頭と末尾の改行を除いた文字列（本文と履歴を分けずにそのまま）。
  - 理由：手で書いた本文や履歴は形がそろうとは限らず、分けると読み違える。エージェントは見出しで分けて読める。
- 位置を求めるために `queue.md` とそのタスクを読むので、キューにある別のタスクのファイルが無い・壊れているときは、`wq list` と同じエラーになる。

### `wq move <ID> <行き先>`（2026-11-25 決定）

| 引数 | 内容 |
| --- | --- |
| `<ID>` | 必須。位置を持つタスク |
| `--to <N>` | 位置 `N`（整数）へ |
| `--top` | 先頭へ |
| `--bottom` | 末尾へ |
| `--before <ID2>` | タスク `<ID2>` の直前へ |
| `--after <ID2>` | タスク `<ID2>` の直後へ |
| `--reason <理由>` | 任意。動いたときだけ履歴に書く |
| `--json` | タスクと動かす前の位置を JSON で出す |

- 行き先（`--to`・`--top`・`--bottom`・`--before`・`--after`）は、ちょうど 1 つ（argparse の必須の排他グループ。0 個や 2 個以上は終了コード 2）。
  - 理由：位置の番号で動かす人と、他のタスクを基準に動かすエージェントの両方が打ちやすい。
- 確かめること（どれも終了コード 1、何も書かない）：
  - `<ID>` が位置を持たない：`タスク <ID> はキューにありません`
  - `--to` の `N` が 1 から「位置を持つタスクの数」までに入らない：`位置は 1 から <数> までにしてください: <N>`。先頭や末尾に丸めない（打ち間違いを黙って受け入れないため。`--top`・`--bottom` がある）。
  - `<ID2>` のファイルが無い：`タスク <ID2> がありません`。位置を持たない：`タスク <ID2> はキューにありません`
  - `<ID2>` が `<ID>` と同じ：`タスク <ID> 自身の前後には動かせません`
- 並べ方：位置を持つタスクの並びを `S`、`S` から `<ID>` を除いたものを `S'` とする。`<ID>` を `S'` の添字 `i` に入れる：`--to N` は `N - 1`、`--top` は `0`、`--bottom` は `len(S')`、`--before <ID2>` は `S'` での `<ID2>` の添字、`--after <ID2>` はその `+ 1`。動かす前の位置 `from` は `S` での添字 + 1、動かした後の位置 `to` は `i + 1`。
- `queue.md` の書き直し：`queue.md` の並びから `<ID>` を除き、`i < len(S')` なら `S'[i]` の直前に、そうでなければ末尾に `<ID>` を入れる。`queue.md` に手で残した `done` のタスクの行は、他の行との前後を変えずに残る。
- `from == to` のとき：何も書かず、コミットもしない（終了コード 0）。`--reason` があっても履歴に書かない。
  - 理由：空のコミットや意味の無い履歴を残さない。書きたければ `wq log` を使える。
  - 人向けの出力：`動かしませんでした: <ID> <タイトル>（<from> 番目のまま）`
- `from != to` のとき：
  - `--reason` があれば、タスクのファイルに履歴の行 `移動 <from> → <to>: <理由>` を足して書き、次に `queue.md` を書く。無ければ `queue.md` だけを書く（タスクのファイルは変えない）。
  - コミットのメッセージ：`move <ID>: <from> → <to>`
  - 人向けの出力：`動かしました: <ID> <タイトル>（<from> → <to> 番目）`
- JSON（どちらのときも）：`{"task": <タスクの JSON（position は to）>, "from": <from>}`

### `wq done <ID>`（2026-11-25 決定）

| 引数 | 内容 |
| --- | --- |
| `<ID>` | 必須 |
| `--reason <理由>` | 任意。履歴に書く。やめたタスクなら、やめた理由 |
| `--json` | タスクを JSON で出す |

- `<ID>` がもう `done`：`タスク <ID> はもう done です`（終了コード 1、何も書かない）。2 回目の完了を履歴に残さないため。
- `status` を `done` にし、履歴の行 `完了`（`--reason` があれば `完了: <理由>`）を足してタスクのファイルを書く。次に、`queue.md` に `<ID>` があれば除いて書く（無ければ `queue.md` は書かない）。
  - やめたタスクも `done` にし、`--reason` にやめた理由を書く（「タスク」の状態）。
- 他のタスクの `depends_on` は変えない。依存先が `done` かどうかは読むときに分かり、`wq suggest` が「着手できるようになった」として使う。
- コミットのメッセージ：`done <ID>: <タイトル>`
- 人向けの出力：`完了にしました: <ID> <タイトル>`
- JSON：`{"task": <タスクの JSON（position は null）>}`
- `done` を戻すには `wq edit <ID> --status <状態>` を使う（キューの末尾に入る。下の「`wq edit <ID>`」）。

### `wq edit <ID>`（2026-11-25 決定）

| 引数 | 内容 |
| --- | --- |
| `<ID>` | 必須。`done` のタスクやキューに無いタスクも変えられる。上の「共通」の `<ID>` と同じ |
| `--title <タイトル>` | タイトル。`wq add` のタイトルと同じ規則（`タイトルが空です`・`タイトルに改行は入れられません`） |
| `--status {todo,doing,waiting}` | 状態。`done` は選べない（終了コード 2。`done` にするのは `wq done`） |
| `--kind {manage,implement}` | 種別 |
| `--assignee <名前>` | 担当。`wq add` と同じ規則（`担当が空です`・`担当に改行は入れられません`） |
| `--due <YYYY-MM-DD>` | 期限。`wq add` の `--due` と同じ確認 |
| `--no-due` | 期限を消す（`due: null`）。`--due` とは排他（終了コード 2） |
| `--add-depends-on <ID>` | 依存先に足す。繰り返し可 |
| `--remove-depends-on <ID>` | 依存先から外す。繰り返し可 |
| `--clear-depends-on` | 依存先を空にする。`--remove-depends-on` とは排他（終了コード 2）。`--add-depends-on` と一緒なら置き換え |
| `--body <本文>` | 本文を置き換える。改行（CRLF・CR）を LF にそろえてから、前後の空白を除く。`--body ""` で空にする。複数行でもよい |
| `--reason <理由>` | 任意。変えたときだけ履歴の行の末尾に書く。上の「共通」の理由の規則 |
| `--json` | タスクと変えた項目を JSON で出す |

- 1 回に複数の項目を変えられる。理由：着手と依頼のように、担当と状態を一緒に変えることが多い。1 コミット・1 行の履歴にまとまる。
- 変える項目のオプション（`--reason`・`--json` 以外）が 1 つも無ければ、`parser.error("変える項目を 1 つ以上指定してください")`（終了コード 2）。理由だけを書くなら `wq log` がある。
- `created` と ID は変えない。`title`・`status`・`kind`・`assignee` は必須の項目なので、消す方法は無い。
- 新しい値：指定しなかった項目は今のまま。`depends_on` は、`--clear-depends-on` なら空、そうでなければ今の並びから始め、`--remove-depends-on` の ID を除き、`--add-depends-on` の ID を指定した順に、まだ無いものだけ末尾に足す。無い ID を外しても、もうある ID を足しても、エラーにしない。
  - 理由：エージェントがよくする「1 つ足す」に、今の並びを読まずに済む。まるごと置き換えだと、今の並びを読み落としたときに黙って依存を消してしまう。
- 確かめること（どれも終了コード 1、何も書かない）。この順に確かめる：
  1. ロックの前に：タイトル・担当・理由の規則。本文に `## 履歴` だけの行があれば `本文に「## 履歴」の行は入れられません`（本文と履歴の境目が分からなくなるため）。同じ ID を足しつつ外せば `タスク <ID> を依存先に足しつつ外すことはできません`。
  2. ロックの後に：`<ID>` のファイルが無ければ `タスク <ID> がありません`。`--add-depends-on` の ID を順に、自分自身なら `タスク <ID> は自分自身に依存できません`、ファイルが無ければ `タスク <依存先> がありません`（`done` のタスクは足せる）、循環するなら `依存が循環します: <ID> → <依存先> → … → <ID>`。
  - 循環：足す ID から、各タスクのファイルの `depends_on` を並びの順に深さ優先でたどり、`<ID>` に着けば循環とする。`done` のタスクもたどる。ファイルが無い ID は行き止まり。理由：循環すると `wq suggest` の「着手できるようになった」がいつまでも出ない。最悪はすべてのタスクのファイルを読むが、手で管理する数では問題にならない。
  - もとからある依存先は確かめない。手で消したタスクを `--remove-depends-on` で外せるようにするため。
- 変わったかどうか：項目ごとに今の値と比べる（`depends_on` は順も含める）。どれも同じなら、何も書かず、コミットもしない（終了コード 0）。`--reason` があっても履歴に書かない。`wq move` の同じ位置への移動と同じ扱い。
  - 人向けの出力：`変えませんでした: <ID> <タイトル>（どの項目も今と同じ）`
- 変えたとき：タスクのファイルに、新しい値と履歴の行を書く。次に、状態が `done` から `done` 以外になり、`queue.md` に `<ID>` が無ければ、`queue.md` の末尾に足して書く（`wq add` と同じく末尾。前にいた位置は覚えていない）。`queue.md` に手で残した行があればその位置に戻る。それ以外では `queue.md` を書かない（キューに無い `done` 以外のタスクも、キューには足さない）。
- 本文：front matter の後の Markdown のうち、最初の `## 履歴` だけの行より前（`store/task.py` の `body_of`）。`--body` は、`## 履歴` の行があれば `\n` + （空でなければ `<本文>\n\n`）+ 見出しの行から末尾まで（そのまま）に、無ければ `\n<本文>\n`（空なら `\n`）に置き換える（`replace_body`）。見出しより前に手で書いたものは、本文として置き換わる。
- 変更の文：変えた項目を次の順と書き方で `、` でつなぐ。`タイトル <前> → <後>`・`状態 <前> → <後>`・`種別 <前> → <後>`・`担当 <前> → <後>`・`期限 <前> → <後>`（無ければ `なし`）・`依存先 <前> → <後>`（ID を `, ` でつなぐ。空なら `なし`）・`本文を変更`（本文は長くなるうえ、差分は `data/` の git に残るので、前後の値を書かない）。
  - 例：`状態 todo → doing、担当 me → 佐藤、依存先 なし → 38, 40`
- 履歴の行：`<変更の文>`、`--reason` があれば `<変更の文>: <理由>`。
- コミットのメッセージ：`edit <ID>: <変更の文>`（理由は入れない。`wq move` と同じ）。タイトルを変えると長くなるが、受け入れる。
- 人向けの出力：`変えました: <ID> <タイトル>（<変更の文>）`（`<タイトル>` は変えた後）
- JSON（どちらのときも）：`{"task": <タスクの JSON>, "changed": [<変えた項目の名前>, ...]}`。名前は上の順の `title`・`status`・`kind`・`assignee`・`due`・`depends_on`・`body`。変えなかったときは `[]`。前の値は履歴とコミットに残るので入れない。
- `store/ops.py` の `edit_task(data, task_id, edit: TaskEdit, reason, now, lock_timeout)` は `EditResult`（`task`・`position`・`changed`・`description`（変更の文））を返す。`TaskEdit` は変える値（`due` と `clear_due`、`remove_depends_on` と `clear_depends_on` の両方は `ValueError`）。

### `wq serve`（2026-11-25 決定）

| 引数 | 内容 |
| --- | --- |
| `--port <番号>` | 待ち受けるポート。既定 `8765` |
| `--no-browser` | ブラウザを開かない。既定では、待ち受けを始める直前に `webbrowser.open` で開く |
| `--json` | 起動時に `{"url": "http://127.0.0.1:<port>/"}` を出す |

- `127.0.0.1` だけで待ち受ける（uvicorn）。人向けの出力は `Worqueue: http://127.0.0.1:<port>/ （Ctrl+C で止める）`。Ctrl+C で止まり、終了コード 0。
- ポートが使われているなどで待ち受けられなければ、uvicorn のエラーのまま終了コード 1。
- ポートは設定ファイルに置かない。今は引数で足りるため（上の「設定」）。
- 書き込みの時刻は `cli/clock.py` の `now`（`web` は `cli` を import しないので、`create_app` に渡す）。

### タスクの JSON（2026-11-24 ユーザー判断）

```json
{
  "id": 42,
  "position": 2,
  "title": "API の設計をレビューする",
  "status": "waiting",
  "kind": "manage",
  "assignee": "佐藤",
  "due": "2026-11-27",
  "depends_on": [38],
  "created": "2026-11-24T09:10:00+09:00"
}
```

- `position` と表の `#` は、`wq list` で出したタスクの中での 1 から始まる位置（出さなかった `done` のタスクは数えない）。`wq add` では、作ったタスクのその位置。
  - `position` は整数か `null`（2026-11-25 決定）。`wq list` で出すタスクでない（`done`、または `queue.md` に無い）ときは `null`。`wq list`・`wq add` ではいつも整数。`wq move` では動かした後の位置、`wq done` ではいつも `null`、`wq edit` では変えた後の位置か `null`。
  - 理由：`wq list` の位置と同じ意味のまま、`done` のタスクも同じ JSON の形で出せる。
- `due` はなければ `null`。本文と履歴は含めない。`wq show` だけは、最後に `"markdown"`（本文と履歴）を足す（上の「`wq show <ID>`」）。

## CI（2026-11-25 決定）

GitHub Actions のワークフロー `.github/workflows/ci.yml`（ワークフロー名 `CI`、ジョブ名 `test`）で lint と型検査とテストを走らせ、結果を PR のチェックとして見せる。

- 契機：すべての `pull_request` と、`main` への `push` だけ。PR ごとの確認と、マージ後の `main` の確認の両方が要るため。他のブランチへの push だけでは走らせない。
- 同じ PR（`main` では同じブランチ）の古い実行は `concurrency`（`group: ci-${{ github.event.pull_request.number || github.ref }}`、`cancel-in-progress: true`）で取り消す。レビューの修正で続けて push しても、最後の head の結果だけを待てばよいため。
- `runs-on: windows-latest` だけで走らせる。ユーザーは Windows で使い、テストは Windows のファイルロックと git for Windows の動きを前提にしているため。ubuntu でだけ壊れる変更は見落とすが、ユーザーの使い方では問題にならないので受け入れる。
- 手順：`actions/checkout` → `astral-sh/setup-uv`（`enable-cache: true`）→ `uv sync --locked` → `uv run -m ruff check .` → `uv run -m ty check` → `uv run -m pytest --tb=short -q` → `uv run -m pytest -m e2e --tb=short -q`。`timeout-minutes: 15`、`permissions: contents: read`。
  - Python は `uv sync --locked` に任せ、`.python-version` の 3.13 を uv が入れる（`actions/setup-python` は使わない）。`--locked` なので、`uv.lock` が `pyproject.toml` と合っていなければ失敗する。
  - git の設定（`user.name` など）は足さない。テストは `tests/conftest.py` の autouse の fixture で、`WORQUEUE_DATA` を一時ディレクトリにし、git をユーザーの設定から切り離し、コミットする人を環境変数で渡すため。`data/` はチェックアウトに無く、`.githooks` も有効にしない。
- E2E（2026-11-25 決定）：`tests/e2e`（マーカー `e2e`）が Playwright と、入っている Chrome（`--browser-channel chrome`）で Web UI を操作する。`pyproject.toml` の `addopts` の `-m "not e2e"` で既定の `uv run -m pytest` からは外し、`-m e2e` で走らせる。windows-latest には Chrome が入っている。
  - 理由：エージェントが画面の動きを自分で確かめられる（ddviz と同じ道具）。既定から外すのは、Chrome の無い環境でも既定のテストを走らせられるようにするため。
  - ドラッグは Playwright の `drag_to` の合成のマウス操作で、OS のドラッグそのものは通らない。
- 型検査は ty（`uv run -m ty check`。2026-11-25 決定）。設定は足さず、既定（`src/` と `tests/` のすべて、`pyproject.toml` の `requires-python`）で検査する。
  - 理由：型ヒントはすべての関数に付ける決まり（`.agents/docs/python.md`）なので、その誤りを PR ごとに見つける。ruff と同じ Astral の道具で、`uv run -m` でそろえて走らせられる。
  - ty の版は dev の依存で固定する（`ty==<版>`、`uv.lock` に入る）。ty はまだ 0.0.x のベータで、版が上がるたびに新しい検査が増えて CI が落ちうるため。版は、指摘を直す手間と一緒に、手で上げる。uv の版を固定しないのと違うのは、uv の更新ではこのリポジトリのコードへの指摘が増えないため。
- uv の版は指定しない（setup-uv の既定の最新版）。`uv.lock` が版をまたいで読めるうちは、版を上げる手間が要らないため。uv の更新で CI が壊れることがありうるが、まれなので受け入れ、起きたらそのときに版を固定する。
- アクションの版は、実装した時点の最新版のタグで指定する（コミットの SHA では固定しない。自分専用のリポジトリでは、そこまでの供給網の脅威は小さいため）。
  - `actions/checkout` はメジャー版のタグ `@v7`。
  - `astral-sh/setup-uv` は `@v10.4.0`。setup-uv は v8.0.0 からメジャー版・マイナー版のタグを出さなくなり（版のタグは変更できないリリースだけ）、`@v10` が無いため（2026-11-25 確認）。

```
  cli/             CLI（argparse）。store を使う
    app.py         パーサーの組み立て、エラーの出力、終了コード、main

    move.py        wq move
```

- 新しいコマンドは `cli/` に 1 コマンド 1 モジュールで足し、データの読み書きは `store/ops.py` の操作にする。
