# Worqueue 仕様

プレイングマネージャー向けに、優先順位の可視化とタスク管理をまとめたアプリ。自分の実装の仕事と、チームの管理の仕事を 1 か所で俯瞰し、次に何をするかを決める。

## 名前（2026-11-22 ユーザー判断）

| 項目 | 内容 |
| --- | --- |
| 表記 | Worqueue |
| 読み方 | ワーキュー |
| 由来 | Work + Queue |
| リポジトリ名・パッケージ名 | `worqueue` |

- 理由：仕事を一覧するだけでなく、順番を決めて処理する（並べ替え、着手、委譲する）という意味がはっきりしているため。元の `Workqueue` のままだと一般的すぎるので、綴りを崩して造語にした。
- 候補だった `Workmap`（俯瞰を表す）と `Taskmix`（管理と実装の混在を表す）は採らなかった。

### 名称の重複（2026-11-22 時点の調査）

| 対象 | 結果 |
| --- | --- |
| Web 上の既存製品 | 完全一致する主な製品は見つからなかった |
| PyPI の `worqueue` | パッケージ情報の API は 404。新規に登録できることまでは確かめていない |
| GitHub | 完全一致のリポジトリは検索で見つからなかった。検索結果を直接取れず、確定はしていない |
| ドメイン `worqueue.com` | 2022-08-22 の登録記録がある。今の登録・利用の状況は確かめていない |
| 商標 | 公式のデータベースでの照合は済んでいない |

- 似た名前の既存のもの：`WORQUE`（オランダの勤務スケジュール管理アプリ）、`WorQ`（PyPI の Python のタスクキュー）。短縮形の `Worq` は `WorQ` とぶつかるので使わない。
- `Worqueue` の綴りは、過去の技術文献やソースコードにも使用例がある。
- 公開・配布の前に、GitHub のリポジトリ検索と J-PlatPat（`Worqueue`、`ワーキュー` と似た表記）で最終確認する。

## 解きたい課題

- プレイングマネージャーは、管理の仕事（レビュー、調整、メンバーへの依頼）と実装の仕事が混ざり、どれを先にやるべきかを判断しにくい。
- 自分の手元の仕事と、チームに振った仕事の全体像を同時に見たい。
- 単なる ToDo リストではなく、優先順位・進捗・依存関係を見て、次に着手する仕事を決められるようにする。
- タスクだけでなく、作業の履歴や判断（なぜその順にしたか）も残す。

## 要件

| 項目 | 内容 |
| --- | --- |
| 利用者 | 自分専用。自分のタスクと、チームに振った仕事を自分ひとりで管理する。他のメンバーは Worqueue を触らない（2026-11-22 ユーザー回答） |
| 操作の入口 | CLI とローカルの Web UI。登録や更新などの操作は CLI で行い、俯瞰はブラウザで開くローカルの Web 画面で行う（2026-11-22 ユーザー回答） |
| データの置き場 | ローカルのテキストファイル。git で履歴を残せて、エージェントも直接読めるようにする（2026-11-22 ユーザー回答） |
| エージェントとの連携 | CLI の JSON 出力。エージェントは CLI を実行してタスクを読み書きする（2026-11-22 ユーザー回答）。MCP サーバーと、Orca のワーカーなどへのタスクの委譲は、今は対象にしない |
| Python | 3.13（`.python-version` と `pyproject.toml`） |

### 方針案（未確定）

- データ：1 タスク = 1 ファイルにすると、git の差分が読みやすく、エージェントが 1 件だけ読み書きしやすい。形式（Markdown + front matter、TOML など）は未定。
- CLI：すべてのコマンドで JSON を出せるようにし（例：`--json`）、人向けの表示とエージェント向けの出力を同じコマンドで賄う。JSON の形はエージェントが頼るので、変えるときは spec に書く。
- Web UI：ローカルのサーバーを立ててブラウザで開く。CLI と同じデータを読み、俯瞰（優先順位、進捗、依存関係）を見せる。編集を Web UI でもできるようにするかは未定。
